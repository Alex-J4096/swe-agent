2026 年 11 月 13 日，C1 已接入 `experiments.transfer_run`。首轮使用 `transfer-four-arm-v2`，实际执行 A1/T1 的 16 个后续任务，C1 的八个因观察前置要求未满足而跳过，见 [首轮结果](three-scenario-01-results.md)。v3 补跑随后在学习阶段因同步修改闲置配置而未通过，未进入观察和后续任务。`transfer-four-arm-v4` 已独立完成 C1 八个后续单元，五个严格通过，见 [C1 补跑结果](c1-transfer-v4-results.md)。下面说明两次指令修复及共用流程。

## v4：明确学习阶段只修改实际生效的配置

v3 学习指令仅要求超时调到 30 并验证，模型实际把两份配置都同步到 30；服务运行成功，但闲置配置全文不变的学习验收未通过。这次记录保存在 `.swe-agent/experiments/c1-transfer-v3-01/`，八个后续单元仍全部跳过，不能视为观察指令修复失败。

v4 保留学习目标，在统一驱动的 C1 学习指令中补充：

> 只修改服务实际使用的配置文件，不要同步修改未使用的配置文件。保持启动代码、无关配置字段和现有文件集合不变。

这条指令没有指定正确配置文件名。验收、记忆机制、预算及后续任务指令保持原样。v4 使用新目录和新学习／观察，不把前置失败删除或算成重试成功。

## v3：明确 C1 观察的执行要求

统一驱动中的 C1 观察指令现为：

> 请读取服务启动代码，说明启动时实际加载哪个配置文件。请实际执行 `python3 service.py`，根据执行输出报告当前生效的超时值和命令退出状态。不要修改任何文件。

这条指令不给出正确配置文件名或期望数值，两个现场使用同一条指令。源码需进入后续模型请求、实际执行必须成功且输出 30、任务文件不变等验收门槛继续保留。只声称超时为 30，没有实际执行回执，仍判为前置未通过。

修改限定于统一驱动的指令生成；旧 `experiments.c1.fixture.OBSERVE` 和历史 C1 驱动保持原样。v2 的八个缺失单元仍保留跳过状态，后续补齐使用新版本、新 LAB 和新的学习／观察轨迹，不回填原批次。

## 研究比较与规模

三个任务分别测试配置入口（C1）、通知后端（A1）和测试入口（T1）的旧经验迁移。每个任务有一个稳定现场和一个变化现场，每个现场比较无记忆、完整历史、默认记忆和自动修订记忆四组。因此，一轮包含六个现场、24 次后续任务；学习、观察和维护另行记录，不能当作额外的独立后续样本。

| 条件 | 新会话输入 |
| --- | --- |
| none | 当前任务与工作区，不携带历史和记忆 |
| full | 当前任务与学习、对应观察的原角色消息，不携带额外记忆 |
| default | 当前任务与默认 worker 维护后的记忆，不导入过去消息 |
| revise | 当前任务与修订 worker 维护后的记忆，不导入过去消息 |

## 各任务共享的流程

1. 每个任务只采集一次默认机制下的自然学习，等待后台维护完成并独立验收。失败则保留输入、日志和验收，不在同一批反复重试。
2. 从同一次学习建立稳定和变化现场。每个现场只采集一次观察，要求识别当前入口的工具结果实际进入之后的前台模型请求；只读取源文件而未送入后续请求，不算完成观察。
3. 观察时携带学习记忆，暂缓后台维护。随后两种 worker 分别从同一学习记忆和相同观察维护输入开始，保存各自记忆快照。不得让 revise 接着 default 的输出继续修订。
4. 四组分别恢复对应现场，开启新会话和新选择缓存。完整历史保留原始角色、tool_calls、tool_call_id 和工具回执，逐次核对实际请求；默认与修订组仅带各自记忆。
5. 按随机顺序执行后续任务，保存第一次文件变更的快照或实际命令执行记录，并独立验收最终状态。无记忆与完整历史组不触发记忆维护，另外两组等待正常维护结束。

当前驱动每个单元只运行一次。`--seed` 仅固定运行顺序，不能固定模型采样或服务端权重。独立重复应使用新的 LAB，重新采集学习和观察；正式批次的重复次数需在开始调用模型前确定。

## C1 的接入规则

初始工程仍包含 `settings.toml`、`app.toml` 和 `service.py`，两份配置初始超时均为 10、端口为 8080。学习要求当前有效超时成为 30，同时保留闲置文件、启动器、无关字段及文件集合；agent 必须实际执行服务验证。

学习成功后，将闲置配置同步为 30，保留已学的有效配置。稳定与变化现场仅在 `service.py` 的加载目标上不同，两者执行都输出 30，不能凭数值判断入口。观察要求当前加载代码进入后续请求，并实际运行服务确认 30。

后续任务统一要求超时改为 60。C1 的 `first_action` 按第一次文件变更涉及的目标分为 correct、inactive、both、other、none；correct 只表示首次修改涉及当前配置，不表示当时已通过行为验收。`first-grade.json` 独立执行首次快照，最终 `grade` 独立执行最终工程。

严格成功除运行时输出 60，还要求启动器和端口不变、闲置配置全文不变、文件集合不变。这样能区分改错入口、双写配置、改启动器输出固定值和添加额外文件等情况。此前 C1 历史结果没有这套新增严格判分，不能直接合并计数。

C1 批准既有 `service.py` 的直接 Python 调用、常用隔离参数及工作区内的单个 cd 前缀；复合验证、重定向和额外脚本不额外批准，工具描述会告知允许形式。普通读取沿用既有权限策略。A1/T1 的任务专属验收与命令限制继续见 [试跑协议](a1-t1-pilot.md)。

## 成本与记忆审计

每个任务的 `costs.json` 分别列出共享学习（前台与记忆）、每个现场的观察、两种观察后维护的 token 消耗。各维护目录另有 `cost.json`。后续任务行的 `agent` 和 `post_memory` 分别记录该组前台与结束后的维护成本。共用准备成本不可重复算作四组各自的一次独立经历；有请求却缺失 usage 时保留 null。

`learning-memories.json` 保存自然形成的可跨会话笔记、project 类型事实数量和相关旧记忆的待复核标记。空库标为没有相关旧记忆；有笔记时需核对内容后分层，不能仅凭数量判断。不得人工补笔记替代自然提取。空库样本能检验新增路径，但不能证明旧事实修订有效。

## 运行与证据

从仓库根目录执行，LAB 必须是新目录：

```bash
uv run python -m experiments.transfer_run .swe-agent/experiments/three-scenario-v4-01 --seed 1134
```

默认选择 C1、A1、T1。只执行 C1 的八个后续单元时：

```bash
uv run python -m experiments.transfer_run .swe-agent/experiments/c1-transfer-v4-01 --tasks c1 --seed 1134
```

开始正式批次前，提交并固定包含当前驱动的版本及提示、预算和评分规则。运行保存 manifest（协议、Git 提交、平台、Python、模型、预算、提示和顺序）、源码压缩包及 SHA-256、各阶段 JSONL、原角色历史、维护输入、前后快照、独立判分、共享成本和失败记录。数据库、评测源码和实验记录位于任务沙箱之外。

旧 `experiments.c1.run` 继续复现三组 C1 与 exposure-pair 历史实验；新的四组批次使用上述统一入口。

## 本地验证边界

当前实验相关测试共 87 项通过。C1 相关回归包括评分、真实验证命令、共享准备、四组隔离、真实 AgentRunner 的原角色导入，以及主入口实际调度 24 个单元。v3 新增两个确定性分支，验证指令实际送达、既有服务命令确实执行时验收通过，以及仅从源码推断并声称数值时验收仍不通过。模型响应使用模拟数据，命令在临时工程真实执行；调度测试另使用模拟隔离结果。这些检查不证明真实模型一定遵循修复后的指令。

v2 的 macOS 实际 sandbox-exec 预检另完成 14 项控制（两个现场各六项、学习阶段两项）和外部文件隔离，模型调用为 0。本机证据在 `.swe-agent/experiments/c1-four-arm-protocol-01/`，含控制结果、验证摘要、当时源码哈希及预检脚本。Linux 尚未对统一驱动完成端到端验证。真实模型结果与缺失单元另见上述首轮报告。
