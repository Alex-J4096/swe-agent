# 仓库变化后跨会话记忆：统一协议首轮结果

后续工程进展：统一驱动 v3 已明确 C1 观察阶段实际执行服务的要求，并通过本地行为回归，见 [协议修复说明](three-scenario-protocol.md)。本文保留 v2 批次结果，八个缺失单元没有回填，真实模型补齐尚未运行。

2026 年 11 月 13 日，本轮计划在配置入口（C1）、通知后端（A1）、测试入口（T1）三个任务上，各运行稳定、变化两个现场，并比较四种跨会话信息条件。实际完成 A1、T1 的 **16 个后续任务**，其中 **14 个通过严格验收**。C1 的变化现场未通过观察前置要求，其八个后续单元按协议跳过，不能计入行为成功率。

完成的单元中，15 次实际目标行动全部命中当前入口，另一次未执行目标操作。自动修订确实改正了旧笔记，但本轮没有观察到它改善首次目标选择或降低整体成本。样本每个单元只有一次，结果用于描述这批轨迹，不能据此估计总体成功率或作因果归因。

## 背景与研究目标

编程 agent 在一个会话中学到的项目经验，可以保存成笔记供以后会话读取。仓库改版后，这些经验可能仍然正确，也可能过时。本研究关注：旧记忆能否减少重新检查，还是会使 agent 第一次操作命中过期入口，即便最后经过返工仍能完成任务。

此次还比较自动修订机制：当 agent 已经看到当前仓库的新证据后，由独立记忆子智能体搜索、读取并修改相关笔记，是否比原有记忆维护更有用。默认提取和检索机制保留为基线。

## 方法与固定版本

运行提交为 `a4f457cb715cb3239a8bce6753e5e35dcc083ddd`，协议为 `transfer-four-arm-v2`。平台为 macOS sandbox-exec，模型请求与返回标识均为 SiliconFlow `deepseek-ai/DeepSeek-V4-Flash`。前台正常输出预算为 1,024 token、最多十轮工具迭代，沿用截断恢复；修订子智能体为 4,096 token、最多八轮。seed 1134 只固定执行顺序，不固定模型采样或服务端权重。

每个任务先采集一次成功学习和自然记忆，再从这一次学习分别构建稳定、变化现场；每个现场只采集一次观察。两种记忆 worker 使用相同学习记忆和相同观察维护输入，各自维护后再开启四种新会话：

| 条件 | 后续会话可用的信息 |
| --- | --- |
| 无记忆 none | 当前任务与仓库，不带前序历史和笔记 |
| 完整历史 full | 学习及对应观察的原角色消息，不额外注入笔记 |
| 默认记忆 default | 默认 worker 维护后的笔记，不导入过去消息 |
| 自动修订 revise | 修订 worker 维护后的笔记，不导入过去消息 |

C1 任务要求将服务有效超时从 30 改为 60，变化现场切换配置加载文件；A1 要求给订单取消流程增加通知，变化现场切换应用实际消费的通知后端，旧后端仍可调用；T1 要求执行当前 CI 指定的定价测试并报告结果，变化现场将脚本 A 切换为脚本 B，两条脚本仍然都能执行。

A1 按第一次文件变化后的工程判定通知路线，并独立检查最终业务行为、幂等性、创建流程回归、装配和文件集合。T1 用实际执行记录判定测试入口和报告，不接受模型自称运行。预置断言失败、退出码为 1 是 T1 的正确观测结果，不等于任务失败。

## 前置条件与缺失单元

三个任务都通过了学习验收，且自然形成了相关旧记忆：C1 一条配置文件事实；A1 两条旧通知装配及创建流程事实；T1 三条项目笔记，其中一条直接记录旧 CI 入口。此次 A1 有真实的旧记忆可修订，不能与此前没有形成旧笔记的 A1 试跑混为一谈。

C1 稳定现场完成了读取加载代码、实际运行和两种维护。变化现场也读到了当前 `service.py`，并在后续请求中正确说明使用 `app.toml`、旧记忆与现场冲突，但没有实际执行服务，因此 `runtime_requirement_met=false`。按任务级前置规则，稳定和变化现场的八个后续单元全部跳过。

这里暴露了观察指令与验收要求的明确性不足：指令写的是“读取……说明……确认当前生效的超时值”，而验收另要求实际运行。统一协议时没有把执行要求明确写进指令。该前置失败不能解释为旧记忆导致误改，也不能通过事后放宽门槛纳入本轮。缺失的 C1 数据需要在对齐要求后另开批次补齐。

两次严格未通过都保留在 revise 组计数中：

- **T1 稳定／revise：未执行目标测试。** 前台读取项目后，把 run_bash 的 DSML 标记写进普通回复，返回消息没有结构化 tool_calls，实际目标运行次数为零。文件未改，也没有选错测试入口的执行记录。runner 的 ok=true 不能代替独立任务验收。
- **A1 稳定／revise：业务通过，文件集合不通过。** 取消通知、创建回归、幂等性和订单号均正确，但前台额外写入 `.claude/memories/order-cancelled-event-emission.md`，并耗尽十轮工具迭代。该文件是前台通过普通文件工具写出的，不是后台修订工具的新增。不能把这次严格失败描述为改错通知后端。

本轮没有观察到首次操作命中过期目标。上述可见失败原因也不足以证明它们由修订机制导致；同样不能因其原因不同而把失败从 revise 组结果剔除。

## 记忆机制观察

在 A1 变化现场，默认维护保留了“EventBus 未订阅、应使用 LegacyNotifier”的旧事实，并新增当前 EventBus 已订阅的事实。修订维护则修改原有两条笔记，将当前后端、创建流程和调用方式更新为 EventBus。

在 T1 变化现场，默认维护新增 CI 使用脚本 B 的纠正笔记，同时保留脚本 A 为当前入口的旧笔记；修订维护更新原 CI 入口笔记，并保留仍正确的旧测试缺陷说明。两组的后续任务都实际执行了脚本 B，因此本轮不能把更一致的笔记直接等同于更好的行为结果。

T1 变化／revise 的任务后维护还创建了运费缺陷笔记，引用真实测试退出码 1 的 `command_failed` 证据，并保留 `ok=false`，同时引用源码读取证据。这次真实模型调用实际使用了之前修复的非零执行证据路径，不再只是确定性提案重放。所有修订子智能体正常结束；全批次没有 model_error、memory_maintenance_error，也没有 invalid_evidence 或 claim_mismatch 拒绝。

## 分析与边界

自动修订这次能够依据观察纠正自然生成的过期事实，功能链路成立；但比较目的仍是后续行动与成本。本轮默认记忆即使保留了冲突笔记，仍首次命中并最终完成任务，无记忆组也全部命中，尚未暴露需要修订来挽救的过期入口误操作。

与默认组相比，修订组总 token 在 A1 为约 **2.49 倍**，在 T1 为约 **2.11 倍**，重查数也没有减少。完整历史在 T1 中减少检查且 token 更少，在 A1 中虽然少检查，反复携带历史使 token 更高。因此，不能用“少读了几个文件”代替整体执行成本。

本轮有 22 次工具权限拒绝，复合命令限制可能增加尝试和工具轮数，属于执行条件的一部分。结果只有每单元一次、两个完成任务、一个缺失任务，且模型输出有随机性。它既不能证明修订普遍无效，也不能证明模型升级已经解决旧记忆问题，更不能由当前批次归因于某次模型或架构升级。

下一步先对齐 C1 观察指令与执行验收，保留本轮缺失记录，再独立补齐 C1；工具格式和额外工作区记忆文件需先明确记录与处理口径。当前证据不足以支持继续叠加新的遗忘机制，或扩展 C2/A2/T2 来替代这些未解决的执行问题。
