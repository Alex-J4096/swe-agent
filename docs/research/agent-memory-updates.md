# 代码改版后，AI 编程助手还会照着旧经验改错文件吗？

让它先学会维护一个项目，再让它亲眼看到项目改版，最后开一个新对话，请它继续干活。想知道，记住以前的工作，到底能帮它少查几次代码，还是会让它改错地方、多做一遍。

举个例子。第一次，我请助手把服务超时改成 30 秒。它找到旧配置文件，改完并验证成功。第二次，项目改用新配置文件，旧文件还留着。助手读过新的启动代码，能看到程序现在读哪个文件。第三次，我只说 **“把超时改成 60 秒”**。它如果沿用第一次的经验，文件会保存成功，程序实际却仍然等 30 秒。

**怎么比较？** 我会给同一个模型做同一道题，只改变它开工时能看到的过去信息。三组都可以自己查代码。

| 第三次开工时 | 想看什么 |
|---|---|
| 从零开始，只给当前任务 | 自己查出正确位置，要花多少步？ |
| 给它前两次完整的工作记录 | 已经看到旧经验和新证据，它能否用对？ |
| 让助手用自己保存和找回的记忆 | 日常使用的记忆功能，实际帮了忙还是添了乱？ |

我还会在**一直沿用旧配置**的项目副本上重复同一实验。这样既能看到记忆让助手改错的情况，也能看到旧经验依然正确时，它省下了多少工作。这里说的“选择性遗忘”，就是项目改版后能放下失效的经验，项目没变时仍能用上它。

**最后会交付什么？** 一套别人可以复跑的小任务、一张三组结果对照表，以及一条能逐步解释的操作记录。表里看三件事：第一次改在哪里、程序最终是否真的生效、为此读了几次文件和用了多少 token。如果三组最后都改对，仍然可以比较谁直接做对、谁靠返工补救。

C1 的稳定／迁移任务已在 macOS 跑完一次三组对照。六次最终运行值均为 60；首次落点和修改前读取次数存在差异。其余五对任务尚待实现。[逐次结果与证据](c1-pilot-2026-11-12.md)

## 实验协议

实验使用能读写文件和执行命令的终端编程助手。它可以跨对话保存项目经验。模型能看到每条可见记忆的一句话描述，以及检索选中的记忆正文。记录这两部分，可以在出错时追查旧路径究竟出现在哪里。

### 第一步：复现事实更新实验

从 MemoryAgentBench 的 FactConsolidation 入手。先手工追踪一道单跳题和一道多跳题中的旧事实、更新证据和正确答案，再按作者表 5 的 6K 设置运行这两类任务，沿用其提示和评分方法。记录数据版本、模型版本、逐题输出和准确率。如果更换模型，单独列出结果。复现的目的是熟悉如何区分“没有看到更新”和“已看到更新却沿用旧事实”。[论文与表 5](https://arxiv.org/html/2507.05257v4) · [作者代码](https://github.com/HUST-AI-HYZ/MemoryAgentBench) · [公开数据](https://huggingface.co/datasets/ai-hyz/MemoryAgentBench)

### 第二步：在自己的 agent 上做行为实验

以下任务、脚本名与数据规模均为拟议设计。每个任务用一个可在本地运行的小型仓库实现。我们控制软件的真实行为，因此可以用程序判断 agent 是否做对，同时查看它产生答案前实际读取和修改了什么。

以修改超时配置为例，每个任务分三次会话。

1. **获得经验。** 智能体将超时改为 30 秒，通过运行程序确认配置来自 `settings.yaml`。
2. **观察当前状态。** 从同一初始仓库复制两个版本。稳定版继续读取旧文件，迁移版改为读取 `app.toml` 并保留旧文件。让智能体在两个版本中完成相同的只读任务，读取实际启动代码。保存这段交互，确认两个版本都向模型展示了当前入口。
3. **测试后续行动。** 开启新会话，给出同一句指令“把服务超时改为 60 秒”。三个条件从各自版本的同一快照出发，使用相同模型、工具和执行预算。任务脚本独立启动服务或调用配置加载器，验证运行时的超时值。

### 一个完整样例：服务超时设置

仓库同时包含 `settings.yaml` 和 `app.toml`，初始值均为 10 秒。应用启动时只使用其中一个，具体取决于启动模块调用的配置加载函数。两个文件各自还有一个无关字段，便于检查修改是否产生额外影响。

| 会话 | 给 agent 的原始指令 | 实验人员的操作与观察 |
|---|---|---|
| 1 | “请把服务的请求超时调到 30 秒，并验证修改生效。” | 应用此时读取 YAML。记录成功操作和自然生成的项目记忆。若任务未完成，单独登记；此轨迹无法用于研究对成功经验的复用。 |
| 2 | “请读取服务启动代码，说明启动时如何加载配置，并确认当前生效的超时值。只需检查。” | 在会话开始前建立两个分支。两边都把两个配置文件的超时同步为 30 秒，其他内容保持一致。稳定分支沿用 YAML，迁移分支改为读取 TOML。两边运行时都返回 30 秒，所以仅凭数值无法判断来源。检查实际送入模型的工具结果中是否出现了能确定来源的代码。 |
| 3 | “请把服务的请求超时调到 60 秒，并验证修改生效。” | 从两个分支分别启动三种记忆条件。保存第一次修改前后的文件差异。任务结束后，评测脚本在新进程中加载配置，检查实际超时是否为 60 秒，并分别记录无效文件和无关字段是否也被修改。 |

例如，在迁移分支中，agent 可能先搜索代码、修改 YAML、验证发现仍是 30 秒，随后修改 TOML。这个样例应记为“第一次修改命中过期目标，最终成功”。若 agent 第一轮先读启动代码再改 TOML，应记为“首次修改正确，修改前重新检查了环境”。两种轨迹都可能通过最终测试。这里的轨迹仅用于说明标注口径。

### 六对任务怎样构造

表中每行对应一个独立任务，各有一个稳定版本和一个变化版本。稳定版本继续使用原目标，变化版本切换到新目标。两版保留相同的候选文件、接口或命令；正式运行时使用相同的第三轮指令。

| 任务 | 第一轮获得的经验 | 第二轮展示的证据 | 第三轮任务和独立验收 |
|---|---|---|---|
| C1 服务超时 | 修改 YAML 后，运行时返回 30 秒 | 启动模块实际读取 YAML 或 TOML | 调到 60 秒；启动新进程读取有效值 |
| C2 工作进程数 | 将 `worker.ini` 中的并发数设为 2 | 启动器从 INI 或 `worker.json` 加载进程数 | 调到 4；用测试执行器截获创建进程池时传入的大小 |
| A1 通知发送 | 在订单创建流程通过旧通知接口发出事件 | 读取应用的依赖装配代码，观察实际注册的通知后端及调用签名 | 给订单取消流程增加通知；驱动一次取消操作，检查当前后端收到且只收到一条含订单号的事件 |
| A2 缓存清理 | 在账户停用流程中用旧缓存接口清除资料 | 读取请求处理器，确认当前使用旧缓存还是新版命名空间缓存 | 让修改昵称后也刷新缓存；先预热资料缓存，再修改昵称，验证下一次读取取得新值且其他账户的缓存仍在 |
| T1 单元测试入口 | 运行脚本 A 执行定价单测，能识别已知失败 | 读取当前 CI 作业，查看它调用脚本 A 还是脚本 B | “运行项目当前的定价单元测试，报告失败的用例”；两脚本都可执行，评测核对实际执行记录与预置失败用例 ID |
| T2 集成测试分组 | 通过原测试标记运行导入器集成测试 | 读取 CI 中的筛选表达式及测试收集清单，看到标记是否切换 | “只运行当前导入器集成测试，报告运行数量和结果”；评测核对实际运行的用例集合和退出状态 |

接口类任务要让旧接口在迁移后仍可调用，例如旧通知后端仍会接受事件，但当前应用只消费新后端的事件。测试类任务要让旧入口仍能执行一组合理的测试。否则，删除旧文件或让旧命令立即报错，会把任务简化为跟随报错重试。在实现任务仓库时，先由实验人员分别试走旧路径和正确路径，验证评测能区分两种行为。

| 实验条件 | 第三次会话可用的信息 |
|---|---|
| 无跨会话记忆 | 当前指令和仓库工具，关闭记忆注入，并隔离历史会话文件和实验日志 |
| 完整历史 | 当前指令、仓库工具和前两次交互的完整记录，关闭额外记忆注入，确认历史完整放入上下文 |
| 现有记忆 | 当前指令、仓库工具，以及默认机制选出的记忆索引和正文 |

首轮做 **6 对稳定／变化任务**，覆盖配置入口迁移、接口替换和测试命令变化，每类两对。每对运行三个条件，共 36 次第三阶段运行。逐条件重置工作区与记忆，固定模型版本和提示。仅评测脚本持有版本标签与答案。这个规模用于查找现象，报告各组实际次数，并对典型差异重复运行。

## 记录与判断

为使三组看到可比较的经历，同一任务只生成一次第一轮轨迹。随后在稳定、变化两个分支各生成一次第二轮轨迹，等待后台记忆写入完成，分别保存仓库、记忆和对话快照。第三轮的三个条件都从对应分支快照的独立副本启动。若第二轮工具结果没有向模型提供足以识别有效入口的证据，把它标为“未观察到更新”，单列数量。试运行时可据此改进第二轮指令；锁定正式指令后保留所有失败记录。

第三轮使用相同的模型版本、推理设置、任务提示、可用工具和最大工具轮数，随机打乱三组的执行顺序。完整历史组保留原始工具结果，检查实际模型请求是否发生了压缩或截断。无记忆组使用干净的工作副本与新会话，所有条件的运行日志、验收脚本和标准答案均保存在 agent 可访问范围之外。

每次运行前用 `/experiment on <路径>` 开启独立 JSONL 日志，路径选在测试工作区之外。核对 `/experiment status`，完成后用 `/experiment off` 结束。评测脚本另存任务编号、快照版本、实验条件、日志 run_id 和行为测试结果。根据实际模型请求核对索引、正文和工具返回内容，标记新证据第一次出现的位置。

| 指标 | 判定方式 |
|---|---|
| 首次行动正确率 | 对照工具轨迹，判断首次实际修改的目标或首次执行的目标命令是否正确。单列没有执行目标行动的次数 |
| 最终成功率 | 由独立行为测试判定，同时标记“先做错、后修正”的运行 |
| 执行成本 | 记录工具调用次数和输入、输出 token。主任务与后台记忆维护分列，缺失用量标为未知 |

如果完整历史组能做对、现有记忆组先做错，沿“记忆写入 → 检索 → 提示词 → 首次行动”定位差异。若轨迹显示旧索引和新正文互相冲突，再固定正文，仅切换索引是否可见，成对重跑。若三组均能做对，比较稳定和变化场景各自的重查成本；若成本也接近，就报告该设置下未观察到记忆收益。

## 阶段产出

第一轮按“任务 × 分支 × 条件”保留逐次结果。分别报告稳定分支和变化分支中的首次正确次数（各条件分母最多为 6）、最终成功次数、首次修改前的读取次数和总工具调用数。预先约定只读搜索不计为修改，测试命令以实际执行的用例集合判定。同一操作同时改中新旧目标时单列“同时修改”，仅改对目标后仍未通过行为验收的样例也单列说明。若超出预算而没有采取目标行动，计入总运行数并标记“未行动”。用模型请求和工作区差异交叉核对，难以判定的轨迹保留原始记录供复核。

讨论时优先决定两个问题：（1）第二轮明确要求检查启动或 CI 代码，测的是“已经看过证据后能否正确行动”；如果关心 agent 是否会主动发现变化，可另设不提示检查的后续实验。（2）C1 驱动现已支持按原角色导入完整历史、等待后台写入、保存快照、独立验收与逐次汇总。后续任务需要各自的运行时验收与行动判分。首个里程碑是让另一位成员仅凭 C1 的任务仓库、固定指令、日志和判分规则，独立复核一条轨迹。

先完成一张论文复现结果表，再用一对配置任务跑通三组条件，验证日志足以还原第一次行动。扩展到六对后，整理一张成功率与成本对照表、一条带证据的任务轨迹，以及一页说明适用范围的面试材料。所有数字均以实际运行结果填写。
