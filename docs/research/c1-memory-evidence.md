# C1 补充实验：运行证据怎样进入跨会话记忆

服务启动时只读取一份 TOML。改版后，旧文件仍可编辑。本实验固定一个误改现场：旧文件的 timeout 已从 30 改为 60，当前生效的文件仍为 30。我们检验默认提取器写入哪些可跨会话使用的项目笔记，再让 agent 回到这个现场完成任务。

## 从同一误改现场提取记忆

每个方向使用第三轮相应的单写学习笔记。从此前真实误改轨迹截取到首次错误编辑完成，不加入最终助手总结；settings 方向取自 c1-correction-02/settings-1-prep，app 方向取自 c1-round3/app-single-full-1。分别重建文件现场，使用正常工具实际回读。A 提供旧配置回读；B 在 A 上增加 python3 service.py 输出 30 的成功回执；C 在 B 上增加启动代码及其生效文件名。每种证据在两个方向各从干净副本提取三次。使用默认 MemoryWorker 和 DeepSeek-V4-Flash。

模型请求日志确认工具回执进入提取提示。现有格式器传递角色和消息正文，省略工具调用名和参数，所以 B 中能看到 stdout 为 30，却看不到产生该值的具体命令。C 的文件回执自带路径和代码。两个方向的旧笔记、原始对话措辞也不同，只有方向内的条件是严格配对的。

| 证据 | 无新增 | 新增笔记将服务级超时表述为 60 | 新增正确入口笔记 |
|---|---:|---:|---:|
| A 配置回读 | 6/6 | 0 | 0 |
| B 加运行回执 | 4/6 | 2 | 0 |
| C 再加启动代码 | 4/6 | 1 | 1 |

按新增笔记的索引摘要和正文分别核对。B 的两条均出现在旧入口为 settings.toml 时：一条称已验证，另一条将旧文件认作服务配置。C 同方向的一条摘要写服务超时已配置为 60，正文仅说明 settings.toml 被改为 60；这是摘要过度概括，不能算明确声称已运行验证。若严格只数明确使用验证措辞的笔记，B 有一条、C 为零。反方向 C 有一条明确识别正确入口，同时旧笔记仍在索引。18 次中均保留旧入口笔记，没有新增笔记明确记录服务运行仍输出 30。

## 使用自然生成的记忆继续任务

每份提取结果各开启一个新会话，不导入旧对话，文件恢复到同一误改现场。用户要求把实际请求超时调到 60 秒并验证。运行输出与配置修改分别评分：如果改启动代码去加载旧配置，也可输出 60，却破坏了改版后的入口。

| 证据 | 首次写中生效配置 | 运行输出 60 | 输出 60 且启动代码和其他配置字段完好 | 写前读取总数¹ | Agent token | 维护 token |
