# 自动记忆修订的第一轮评估方案

版本说明：本方案的旧接口批次已完成，见 [第一轮结果](automatic-memory-revision-results.md)。当前 subagent 版本沿用本方案的输入和行为评分重新对照，版本、预算及接口差异以 [固定版本记录](memory-revision-freeze.md) 为准，不把旧批次当作当前机制的结果。

本轮检验一个问题：回合结束后自动修订项目记忆，能否让下一会话更少先改错文件，同时保留稳定项目中仍然有用的经验。本方案采用固定批次，运行后据结果决定机制的去留和下一步开发。

## 比较的机制

所有条件运行同一份实验分支代码，使用同一模型、工具、权限和调用预算。只改变 MemoryStore 的 maintenance_mode。

| 条件 | 回合结束后的处理 |
|---|---|
| default | 原提取流程。 |
| evidence | 提取时补全工具名称、参数、回执来源。 |
| revise | 使用同样的证据格式，由模型自动决定保留、待复核或修订相关项目事实，同时提取独立的新事实。 |

主比较为 revise 与 evidence，估计整套自动修订实现相对补全来源后的提取流程的收益。default 用于连接已有基线。修订组的候选选择和维护提示也是待评估实现的一部分。所有起点和维护后笔记数须低于十条，防止达到原批量整理阈值；若维护后达到十条，记为协议偏离并单独报告其结果。

## 项目和初始记忆

沿用三文件配置项目。settings.toml、app.toml 都有 timeout 和 port 字段，service.py 决定读取哪份配置并打印 timeout。独立评分器知道入口，agent 需要通过自己的记忆与检查确定入口。

使用此前两个方向的单写学习快照。每个方向只使用该方向同一份原始笔记，所有模式得到字节一致的副本。笔记自然记载上次生效的配置文件。不同方向的笔记措辞及验证偏好可能不同，因此以方向内配对结果为主。

每个起点由程序构造文件状态并实际执行工具，生成按原角色和 tool_call_id 配对的输入消息。实验者控制证据的可得性。记忆内容由真实模型通过正常 MemoryWorker 自动维护，保留旧笔记和工具回执之外不人工加入正确答案或修订建议。第一阶段不生成助手总结，避免任务完成措辞干扰维护判断。

## 三类现场

下表用旧入口 settings.toml 举例。反方向交换两份配置的角色，其他条件相同。

| 现场 | 文件状态和提供给维护器的实际证据 | 应检查的机制表现 |
|---|---|---|
| 稳定 | service.py 仍读取 settings.toml；该文件已从 30 写成 60，另一份为 30。回读修改结果、运行输出 60，再读启动代码。 | 正确入口应继续可用。语义等价的重写可接受；把正确入口撤下、改错或要求重新查找计为有效经验损失。 |
| 迁移，仅有运行冲突 | service.py 已改读 app.toml；误改 settings.toml 为 60，app.toml 仍为 30。回读旧文件，并运行得到 30；本阶段不提供启动代码。 | 能否记录目标尚未生效或标记待复核；是否仍写入“服务已生效为 60”。模型尚无定位新入口的证据，不应声称已验证另一个文件生效。保留或待复核分别报告。 |
| 迁移，入口已查明 | 与上一行同一文件状态和消息前缀，再实际读取 service.py，显示加载 app.toml。本阶段先不修配置。 | 能否根据启动代码替换失效的入口断言，保留同一笔记中的其他有效经验，并同步更新索引摘要。 |

每个现场中，各模式看到完全相同的消息和初始笔记。所有工具回执来自实际调用。独立评分器的额外检查不加入维护输入。日志记录维护器最终请求中的证据内容，核实截断没有丢掉本条件所需的消息。

## 固定样本和运行顺序

两个迁移方向 × 三类现场 × 两次重复，共十二个起点。每个起点复制为三种模式，共三十六次维护。重复从干净副本开始，不让前一次输出成为后一次输入。

每次维护完成后等待 worker 退出，保存笔记和索引快照，再从同一仓库状态启动一个全新会话。统一任务为“请把服务的实际请求超时调到 90 秒，并验证修改生效”。所有模式均开启记忆，清空检索缓存，不导入第一阶段对话；只通过各自维护后的记忆连接两个阶段。共三十六次后续任务，无论前一阶段是否正确修订都计入。

运行顺序用固定随机种子 1133 打乱，最多三个并行进程。后续任务采用现有十轮工具迭代上限和同样的运行验证授权。运行结束保存正常后台维护结果，以便观察待复核条目是否被后续真实证据恢复。首次行为评分使用后续任务开始前的笔记快照。

这十二个起点属于同一任务族的受控条件，重复共享学习历史。以逐对结果和失败轨迹作工程决策，不将其当作十二个独立项目估计总体成功率。

## 记录与评分

第一阶段先评估内容，再看维护器自报的 action 或 status。逐条核对索引、可见正文和实际模型请求，不能仅凭出现 committed 就判修订成功。

| 指标 | 判定方式 |
|---|---|
| 查明入口后的正确修订 | 四个强证据迁移起点中，当前入口准确，过时入口不再作为当前事实可见，其他有效事实保留。 |
| 稳定记忆误伤 | 四个稳定起点中，正确入口被停用、变为错误事实，或出现无证据的待复核提示。 |
| 运行冲突的处理 | 四个弱证据迁移起点分别统计保留、待复核、正确记录未生效、无证据猜测入口、错误记为已生效。 |
| 修订链路损失 | 候选未命中、模型未给决定、非法证据、断言不唯一、版本冲突、取消或维护请求失败。分母包含这些情况。 |
| 内容一致性 | 索引与正文是否一致，原笔记中的验证命令等其他事实是否保留，是否又新增了冲突的别名笔记。 |

后续任务的主要行为指标是迁移现场的首次写入是否只命中当前配置。无写入、先写旧配置、首次同时写两份、先修改启动代码分别列出。额外统计首次写对后又修改闲置文件的次数。

最终严格成功要求实际输出 90、启动代码保持原入口、端口等无关字段完好，且没有新增无关任务文件。同时报告“输出 90”这项宽松结果，以暴露修改启动代码来迎合旧记忆的情况。

返工要求时间顺序明确：先改错，运行发现未达到 90，再做后续修改。写前读取、总工具调用、维护及任务 token、请求失败和执行时间分别记录。维护成本从第一阶段开始计入，后续任务结束后的维护也计入总成本。按成功任务报告总成本，失败任务消耗仍计入总量。

主要配对差值取 revise 减 evidence。分别报告稳定、弱证据迁移、强证据迁移的计数和逐对成本，保留方向信息。人工内容核对先使用隐藏模式名的快照，依据上述口径判分，之后再展开组别。

## 运行前后留下的证据

运行前固定代码提交及工作区补丁摘要、模型实际返回标识、参数、顺序、初始文件和笔记哈希。使用新的独立实验目录，每个任务保存输入消息、维护 JSONL、维护前后笔记、后续任务 JSONL、文件差异、独立运行值和评分。

本轮仅使用项目内存储。真实任务执行沿用 macOS sandbox-exec，测试仓库和记忆逐组隔离。请求错误按现有重试策略处理，错误与消耗保留。实现异常保留为失败；若需要修代码，另存新版本，修正后整批重跑同一计划。

## 跑完以后怎样决定

若强证据仍经常无法定位旧笔记或提交修订，先修复候选检索、输出格式或写入链路；若证据已完整提供而内容判断仍错，调整修订决策规则。稳定场景出现误伤时，优先检查触发依据和待复核规则。

若入口修订正确，并减少迁移后的首次误改或返工，且没有增加稳定场景误伤，则保留可选机制，报告额外维护成本，下一步扩展到新的仓库变更类型。

若笔记改对而下一会话行为没有改善，则本轮对行为收益的结论为未观察到。检查实际展示的记忆与行动是否一致，然后转到更有区分力的项目任务。若三组都首次改对，记录该任务的天花板效应，停止追加同一 C1 条件的重复。

待复核条目在下一任务获取了新证据后能否恢复，从已经计划的后续维护中观察。更大样本和跨项目验证由本轮结论决定。
