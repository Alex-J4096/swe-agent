# A1/T1 四组真实模型链路试跑结果

**2026 年 11 月 13 日｜环境接通与机制边界检查**

本报告保留修复前的试跑结果。后续空库与失败执行证据的工程修复及功能验证见 [修复记录](memory-boundary-fix.md)，没有将修复后的维护回放合入本报告的行为计数。

本轮把自研编程 agent 的跨会话记忆研究，从配置文件迁移扩展到通知后端和测试入口两个任务。已经跑通成功学习、只读观察、两类记忆维护、原角色完整历史导入和独立验收，完成 16 个后续任务。当前结果主要说明链路可以运行，并暴露了正式实验前需要处理的边界，尚不能证明自动修订能跨任务稳定减少误改。

最关键的发现是：**A1 学习期没有形成持久笔记，修订组也未成功创建笔记，因此这组没有实际检验旧笔记更新；T1 形成了旧入口笔记，修订器能够更新它，但后续维护拒绝了有效的“测试已执行、断言失败”回执。**

## 1　研究问题与两个项目

agent 能读写项目文件、执行本地命令，也能把一次对话的经验保存为下次使用的笔记。研究关注：项目改版后，旧经验能否帮助省去检查，还是让 agent 先沿用过时目标；自动修订笔记能否改善下一会话的行为。

A1 是一个订单服务。旧通知客户端和新事件总线始终可调用，但应用只消费其中一个。稳定版继续消费 LegacyNotifier；迁移版改为消费 EventBus。后续任务是在取消订单时发送一条包含订单号的通知，同时保留创建流程和取消幂等性。独立评分器真实驱动两种订单号，检查消费结果、调用后端、重复发送、创建回归及装配是否被改回旧版。

T1 是一个定价项目。两个测试脚本都能运行，CI 决定当前采用哪个。A 脚本执行三条用例，失败项为优惠券导致负总额；B 执行四条用例，失败项为漏加运费。稳定版 CI 调用 A，迁移版调用 B。两套测试都刻意保留一个断言失败，均退出 1。任务是实际执行当前测试集，报告数量、完整失败 ID 和退出码，而不是修代码。评分器检查外部工具执行记录、真实用例集合、文件完整性和最终报告。

两个项目都只用 Python 标准库，在 macOS sandbox-exec 中执行，旧路径不会因删除或不可调用而立即暴露错误。项目结构与独立评分规则见 [环境手册](a1-t1-environments.md)。

## 2　四组共享什么、改变什么

每任务只使用一份通过验收的真实学习记录，并为稳定、迁移项目各采集一次只读观察。观察前台使用学习期的默认记忆；观察后，将相同维护输入和相同学习笔记分别交给默认 worker、修订 worker。没有为修订组重新采样一段更好的经历，也没有人工补写旧笔记或正确答案。

| 后续条件 | 新会话获得的信息 |
|---|---|
| 无记忆 | 当前项目与当前任务，无前序笔记或对话。 |
| 完整历史 | 学习及对应版本观察的完整原角色消息，不注入额外笔记。 |
| 默认记忆 | 默认 worker 维护后的笔记，不导入过去对话。 |
| subagent 修订 | 修订 worker 维护后的笔记，不导入过去对话。 |

每任务 × 两版本 × 四组，各条件只执行一次，共八次。两任务合计十六次。顺序 seed 为 1134；单进程顺序运行。模型沿用 SiliconFlow 的 deepseek-ai/DeepSeek-V4-Flash，前台正常输出上限 1,024 token、最多十轮工具迭代；修订 subagent 沿用 4,096 token、八轮及既有截断恢复。T1 统一要求最终给出数量、失败 ID、退出码的 JSON，缺字段不会用标准答案补齐。

模型采样未固定，每个任务只有一份学习历史，因此这些运行不是独立项目样本。A1 和 T1 在不同驱动试跑版本中完成，各自保存提示、顺序、源码压缩包和哈希。agent 的 main.py 与 src 始终与固定提交 86c1370 一致。

## 3　为什么保留了四个试跑目录

| 目录尾号 | 实际发生的事情 | 纳入的后续任务 |
|---|---|---:|
| pilot-01 | A1 学习同时调用两个后端并改动装配，未通过前置验收；T1 独立通过学习和观察。 | T1 八次 |
| pilot-02 | 给 A1 补明保持装配、接口及单后端发送的范围约束。代码业务行为正确，但驱动拒绝带 cd 前缀的验证命令，模型又新增验证脚本，未完成合规验证。 | 零 |
| pilot-03 | 支持单个 cd 前缀，但仍拒绝多个合法 CLI 与 echo 的组合。学习又留下额外验证文件，未通过前置验收。 | 零 |
| pilot-04 | 完整适配工作区内 cd、既有 CLI、echo 的顺序组合，并在工具描述中说明允许的验证形式；真实 CLI 本地回归通过后，A1 学习、观察和八个后续任务全部接通。 | A1 八次 |

前置失败都保留，没有在同一批中修改代码、覆盖失败或代写成功学习。02、03 的 A1 实现已具备正确业务行为，失败同时涉及驱动命令限制、验证未完成和额外文件，不应全部归为模型不会实现通知。完整约定见 [试跑协议](a1-t1-pilot.md)。

这些经历也说明，直接把 C1 的单命令白名单移到较复杂任务，会引入与记忆无关的失败。即使在 pilot-04，带目录列举或重定向的其他复合验证形式仍有拒绝记录；它们保留在成本及失败诊断中，正式协议需要明确这一采集边界。

## 4　后续行为结果

每行合并同一任务的稳定、迁移版本，分母为两次。A1 首次行动根据第一次实际修改后的独立项目副本运行行为探针判定；T1 根据首次真实执行的测试入口判定。

| 任务 | 条件 | 首次正确 | 最终严格验收 | 写前／执行前成功读取 | 前台工具调用 |
|---|---|---:|---:|---:|---:|
| A1 | 无记忆 | 2/2 | 2/2 | 10 | 18 |
| A1 | 完整历史 | 2/2 | 2/2 | 0 | 5 |
| A1 | 默认记忆 | 2/2 | 2/2 | 8 | 19 |
| A1 | subagent 修订 | 2/2 | 2/2 | 8 | 20 |
| T1 | 无记忆 | 2/2 | 2/2 | 11 | 17 |
| T1 | 完整历史 | 2/2 | 2/2 | 0 | 2 |
| T1 | 默认记忆 | 1/2 | 1/2 | 11 | 18 |
| T1 | subagent 修订 | 2/2 | 2/2 | 12 | 21 |

A1 八次都首次调用当前后端，没有首次误发旧后端或双发，也没有因这些错误产生返工。迁移版修订组触及十轮工具迭代上限，前台返回未正常完成；但它此前已实际运行取消 CLI，返回正确通知，独立评分也确认代码、创建流程和幂等性完好。因此保留“业务严格验收通过、前台达到预算上限”两个事实。

T1 的七次实际目标执行都首次选对入口。迁移版默认组未执行目标测试：模型把 DSML 工具调用语法放入普通文本，SDK 响应没有可执行的结构化工具调用，agent 将它当作最终回复结束。该次既无目标执行回执，也无完整结果报告，计为未行动及最终失败。它不是一次“先选旧入口”的轨迹，不能据此认定过时记忆导致误选。

完整历史组在四次任务中都没有重新读取文件便采取正确行动。A1 相对无记忆省去了十次写前读取，但前台 token 更多；T1 同时省去读取与部分 token。节省检查与节省 token 需要分别观察。

## 5　记忆到底发生了什么

### A1：没有旧笔记，空库分支没有成功落盘

A1 的成功学习提取器明确返回空数组，没有留下持久笔记。默认 worker 在观察后生成了稳定版四条、迁移版五条项目笔记，但这些是新观察形成的事实，不是旧笔记纠错。迁移版默认笔记还有一处过度概括，把尚未实现的 cancel_order 也描述成已调用 EventBus；功能任务通过并不等于每条笔记都准确。

修订 subagent 搜索和列举都得到空库，却反复尝试更新不存在的 notification-wiring.md，猜测版本为 1、first、base 或 new，被 read_required 拒绝。稳定观察后的最终回复带大量解释和嵌入 JSON，未通过现有解析；迁移观察后的维护触及迭代上限。两个修订组开始后续任务时都仍无笔记。

日志进一步证明：同一版本下，无记忆组与修订组的首个模型请求 messages 和 tools 完全相同。两者后续检查次数或成本的波动不能解释成修订后的记忆内容不同。本次 A1 测到了空库分支、正常任务能力和完整历史使用，未有效覆盖“已有旧笔记被自动修订”的机制问题。

### T1：入口更新成功，但测试失败证据被拒绝

T1 学习留下两条项目笔记：CI 通过 A 运行，以及旧定价函数的行为要求。迁移观察后，默认维护追加 B 入口笔记，同时保留 A 仍为当前入口的旧说法；修订维护则把原 CI 笔记改为 B，并保留另一条定价规则。两次观察后的修订都提交成功。

问题发生在后续任务结束后的维护。实际测试已执行，回执包含正确用例、失败 ID 和退出码 1，但 run_bash 的 ok 为 false。当前证据白名单只纳入 ok=true 的回执，因而把这些执行观察排除。两次后续维护共发生五次 invalid_evidence，其中四次唯一不合格引用就是仍在证据窗口内的真实测试回执；另一次还混有错误拼接或不存在的 ID。不能把五次全部解释成同一种引用问题。

两次后续修订均达到八轮上限，期间仍有更新成功提交。需要同时看有效更新和未完整结束，不能只统计 committed。

## 7　正式实验前的研究决策

本轮到此停止增加试跑样本，先处理已经定位的边界：

1. 明确定义修订器的空库分支。没有可更新笔记时，应正确结束或通过规定渠道新增独立事实，不能猜文件名、版本并反复更新。用本轮真实失败轨迹作回归，默认记忆基线保持不变。
2. 区分“命令成功执行且断言失败”与“工具未执行、权限拒绝或超时”。退出码非零的诊断信息可以成为“观察到失败”的证据，不能因此被写成“功能验证成功”。先验证这一证据分类规则。
3. 正式数据按是否形成相关旧记忆分层。自然学习后没有笔记，应记为未形成旧记忆，不能把空库条件当作修订实验成功。若另做人工固定旧笔记的受控试验，必须单列为机制测试，不冒充自然学习结果。
4. 锁定命令适配、工具调用文本化的计分与恢复规则、前台预算及正常结束指标。程序可运行的代码、agent 自己完成验证、前台正常结束和后台维护完整结束分别记录，再冻结正式版本。

T1 已证明当前入口证据能进入请求并更新既有笔记；A1 的完整任务链路已接通，但未满足旧记忆修订的实质条件。先修这两类维护边界，比直接扩大六场景正式批次更有依据。

## 8　证据、核验和适用范围

数据位于当前 worktree 的 .swe-agent/experiments/a1-t1-pilot-01 至 pilot-04。T1 有效后续任务在 01，A1 在 04；02、03 保存前置失败。各目录的 manifest.json 与 sources.zip 标识实际驱动版本，不能只用共同的 Git 基底提交代替源码版本。

学习、观察和逐组目录保留原始 JSONL、history.json、维护输入、任务和记忆快照、最终文件及评分；A1 还保存首改项目与首改评分，T1 保存工具执行层 command journal。pilot-summary.json、pilot-verification.json 及对应核验脚本保存汇总和一致性检查。跨批诊断位于 a1-t1-pilot-audit-01/diagnostics.json，包含空库、证据拒绝、预算和源码一致性记录。

核验通过：每任务每版本的四组任务文件一致；原角色历史完整进入请求；无记忆和完整历史不携带旧笔记；默认与修订的维护输入一致，各自使用正确的维护后快照；所有模型请求均有响应和 token。四批中的 agent 核心源码一致，pilot-04 运行结束、报告编辑前的源码快照与工作区已有文件一致。全量代码测试为 318 项通过、1 项跳过。

这是单模型、两种微型项目、每条件一次后续任务的工程试跑，维护内容由本次助手核对，未进行独立人工盲评。没有不可变模型权重版本、新旧模型或架构独立对照，不能据此判断模型升级是否解决了记忆过时问题。
